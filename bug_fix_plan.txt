# Fix #2: "Start chat" from Discover races the action-sheet's close

## Context
Fix #1 (already implemented & merged) replaced the non-existent `page.open`/
`page.close` calls in `discover_view.py` with the correct Flet 0.84
`show_dialog`/`pop_dialog` `DialogControl` API — the sheet now opens and closes
as a real modal bottom sheet (150/150 tests green).

The user re-tested and reports the **same underlying symptom persists**, but
with a crucial new clue: *"when i press start chat with user it not open the
chat but after i press to see his profile and return to the discover view and
now press start chat it is working"*. So:

1. Discover -> tap candidate -> tap "התחל שיחה / שלח הודעה" -> **chat does NOT open**
2. Discover -> tap candidate -> tap "צפייה בפרופיל שלו / שלה" -> profile opens fine -> back
3. Discover -> tap candidate -> tap "התחל שיחה / שלח הודעה" again -> **now it works**

This means fix #1 was correct-but-insufficient — there is a SECOND, deeper bug
specifically in the "close the sheet, then navigate" sequence.

## Root cause
`_on_action_chosen` (discover_view.py:256-267) does, back-to-back, synchronously:
```python
self.page.session.store.set(self.SELECTED_PEER_ID_KEY, profile.user_id)
self._close_sheet()        # -> page.pop_dialog(): sync; sends a "close
                           #    BottomSheet" patch via dialog.update()
self.page.go(route)        # -> fire-and-forget!
```

`page.go` is **deprecated** in Flet 0.84 (`.venv/.../flet/controls/page.py:802-817`,
`@deprecated("Use push_route() instead.", ...)`) and its entire body is:
```python
def go(self, route, skip_route_change_event=False, **kwargs):
    asyncio.create_task(self.push_route(route, **kwargs))
```
i.e. it merely **schedules** an async task that, on some later tick of the
event loop, awaits an RPC round-trip to the Flutter client
(`await self._invoke_method("push_route", ...)`) — it does NOT synchronously
update `page.route` or fire `on_route_change` as its own (stale) docstring
claims.

So `_on_action_chosen` fires **two uncoordinated async operations** over the
same client connection with no ordering guarantee:
  (a) `pop_dialog()` -> `dialog.update()` -> sends a "close the modal bottom
      sheet" patch *synchronously*, and
  (b) `page.go(route)` -> schedules a "push a new route" RPC for *later*.

This is a textbook intermittent race: depending on exactly when the scheduled
task runs relative to the in-flight dialog-dismiss animation/round-trip, the
client can drop or misorder the route push the first time, then "settle" into
a working rhythm once the connection has processed a few more round trips
(e.g. after the user successfully does an unrelated navigation like viewing
the profile and coming back).

This also cleanly explains why the bug is ISOLATED to the Discover
action-sheet path: `MatchesView._open_chat` (matches_view.py:224-229) routes to
the exact same `/chat/new` via the exact same deprecated `page.go`, but
**without** a preceding dialog-close to race against — and is not reported as
broken.

## Fix
In `src/views/matching/discover_view.py`:

1. Add `import functools`.

2. Make `_on_action_chosen` `async` and replace the fire-and-forget `page.go`
   with the documented, awaited replacement `page.push_route` — making
   "close the sheet, then navigate" strictly sequential (the sync
   `pop_dialog()` patch is sent, THEN we await the route-push RPC; no race):
   ```python
   async def _on_action_chosen(
       self, sheet: ft.BottomSheet, route: str, profile: UserProfile,
       e: ft.ControlEvent,
   ) -> None:
       self.page.session.store.set(self.SELECTED_PEER_ID_KEY, profile.user_id)
       self._close_sheet()
       await self.page.push_route(route)
   ```

3. Re-wire both buttons that call it via `functools.partial`, mirroring the
   established pattern for async handlers with captured extra args already
   used in `additional_photos_view.py:200-202`
   (`functools.partial(self._on_remove_photo, extra_index)`):
   ```python
   view_button = create_primary_button(
       "צפייה בפרופיל שלו / שלה",
       functools.partial(self._on_action_chosen, sheet, self._VIEW_PROFILE_ROUTE, profile),
       text_size=DS.type.input,
   )
   chat_button = create_primary_button(
       "התחל שיחה / שלח הודעה",
       functools.partial(self._on_action_chosen, sheet, self._CHAT_ROUTE, profile),
       text_size=DS.type.input,
   )
   ```
   (A bare `lambda _e: self._on_action_chosen(...)` would never be awaited —
   Flet's `_trigger_event` only `await`s handlers where
   `inspect.iscoroutinefunction(handler)` is `True`; verified empirically that
   `functools.partial` of an `async def` correctly reports `True` here, exactly
   as `_on_remove_photo` already relies on.)

`_close_sheet` stays as-is (sync `page.pop_dialog()`).

## Test coverage

   route-recording, but awaited — matching the real awaited contract):
   ```python
   async def push_route(self, route: str) -> None:
       self.route = route
       self.go_calls.append(route)
   ```

   (added for fix #1): `chat_button.on_click` is now a `functools.partial`
   wrapping an `async def`, so the test must `await chat_button.on_click(None)`
   instead of calling it synchronously. Assertions on `sheet.open`,
   `SELECTED_PEER_ID_KEY`, and `page.route`/`page.go_calls` stay the same shape.

3. (Recommended — this is the only style of test that could have caught a
   logic-level version of this bug class) Add an integration test using
   `_RoutingFakePage` (test_component_orchestration.py:1132, which drives the
   real `Router.handle_route_change` exactly like the real
   `page.on_route_change` wiring) to exercise `DiscoverView._on_candidate_tap`
   -> tap "start chat" -> assert the **real** `ChatView` lands on
   `page.views[-1]` with the right `peer_id`/`self_id` — proving the
   build/guard/stack path is sound end-to-end, independent of the
   transport-level race that only the live client can fully exhibit.
