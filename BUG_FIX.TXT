================================================================================
  1. Bug Description (Symptoms)
================================================================================

When a user opens the Discover screen ("אנשים שתרצו להכיר"), taps a candidate
from the list, and the Bottom Sheet appears with two actions:
  • "צפייה בפרופיל שלו / שלה"  (View profile)
  • "התחל שיחה / שלח הודעה"     (Start chat)

Observed broken behavior:
  1. One of the two actions (usually the first one tapped) does not respond —
     no screen opens.
  2. The other action on the same sheet always works.
  3. After returning to the main menu, the action that previously failed now
     works on the next attempt.

Reported reproduction paths:
  • Discover → tap candidate → "Start chat"        → chat does NOT open
  • Discover → tap candidate → "View profile"    → works → navigate back
  • Discover → tap candidate → "Start chat" again  → now works

The bug is isolated to the Discover + Bottom Sheet path. MatchesView (opening
a chat from chat history) is not affected — an important clue when tracing the
root cause.


================================================================================
  2. Context — What Was Already Fixed (Fix #1)
================================================================================

Fix #1 (merged) replaced non-existent page.open / page.close calls with the
correct Flet 0.84 DialogControl API: show_dialog / pop_dialog.

Result: the Bottom Sheet opens and closes as a real modal. All 150 unit tests
pass.

However, the underlying user-facing bug persists. Fix #1 was correct but
insufficient. A second, deeper bug remains in the "close sheet, then navigate"
sequence.


================================================================================
  3. Root Cause Analysis
================================================================================

------------------------------------------------------------------------------
  3.1 [Primary] Race condition between pop_dialog() and page.go()
------------------------------------------------------------------------------

Problematic code — discover_view.py, _on_action_chosen (lines ~272-283):

    def _on_action_chosen(self, sheet, route, profile):
        self.page.session.store.set(self.SELECTED_PEER_ID_KEY, profile.user_id)
        self._close_sheet()        # → page.pop_dialog(): sync; sends patch to Flutter
        self.page.go(route)        # → fire-and-forget!

What actually happens:

  (a) _close_sheet() → page.pop_dialog()
      Sends a synchronous patch to the Flutter client: "close the BottomSheet".

  (b) page.go(route)
      In Flet 0.84, page.go() is deprecated ("Use push_route() instead").
      Its implementation is:
          def go(self, route, ...):
              asyncio.create_task(self.push_route(route, ...))
      It only *schedules* an async task that later awaits an RPC round-trip
      to the client (await self._invoke_method("push_route", ...)).
      It does NOT synchronously update page.route or fire on_route_change.

  → Two uncoordinated async operations run over the same client connection:
     (a) dialog close  — patch sent immediately
     (b) route push    — scheduled for a later event-loop tick

  Result: a classic race condition. Depending on timing, the client may:
    • Drop the route push on the first attempt
    • Reorder the RPC messages incorrectly
    • "Settle" after additional round-trips (e.g. after a successful unrelated
      navigation such as viewing a profile and returning)

This explains:
  • Why MatchesView._open_chat (matches_view.py:224-229) is unaffected —
    same page.go(), but no preceding pop_dialog(), so no race.
  • Why "Start chat" works after a successful "View profile" round-trip.
  • Why the bug is isolated to the Discover action-sheet path.


------------------------------------------------------------------------------
  3.2 [Secondary] _sheet_open cleared too early — stacked BottomSheet risk
------------------------------------------------------------------------------

The docstring on _on_candidate_tap (lines ~181-193) states that on_dismiss is
the single place that clears _sheet_open.

However, _close_sheet() (lines ~285-287) also does:
    self._sheet_open = False
    self.page.pop_dialog()

  → The flag is cleared before the sheet dismiss animation completes on the
    client.

  Risk: if the user taps a candidate while the sheet is still closing, a second
  sheet can be pushed onto the dialog stack. The first action-button press
  calls pop_dialog(), which closes only the top sheet — it looks like nothing
  happened. A second press closes the remaining sheet and navigates — it works.

  This matches the symptom: "the first option does nothing; the second always
  works" — especially when two sheets are stacked.

  The guard in _on_candidate_tap (if self._sheet_open: return) prevents
  double-tapping a row, but does not prevent reopening after _close_sheet has
  already reset the flag prematurely.


------------------------------------------------------------------------------
  3.3 [Required for the fix] lambda will not await an async handler
------------------------------------------------------------------------------

Once _on_action_chosen becomes async (as required), wiring it via:
    lambda _e: self._on_action_chosen(sheet, route, profile)
will NOT work. Flet's _trigger_event only awaits handlers where
inspect.iscoroutinefunction(handler) is True.

A lambda wrapping an async def is still a sync lambda — it is never awaited.

Solution: use functools.partial (same pattern as additional_photos_view.py:200-202):
    functools.partial(self._on_action_chosen, sheet, route, profile)
A partial of an async def reports iscoroutinefunction == True, so Flet awaits
it correctly.

  Step A — discover_view.py
------------------------------------------------------------------------------

  A.1  Add import:
         import functools

  A.2  Make _on_action_chosen async and await push_route:

         async def _on_action_chosen(
             self, sheet: ft.BottomSheet, route: str, profile: UserProfile,
